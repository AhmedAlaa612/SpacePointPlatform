**2026-07-26 changes (operator decisions during and after the cutover — `MASTER_EXECUTION_PLAN_V2.md` §B10 has the full reasoning):**
- **Attendance is `present|absent`.** `late` and `excused` are gone (migration `a1d7f36c0013` remaps existing rows). They were also inconsistent: the registrations list counted `late` as attended while the completion rule counted only `present`.
- **Delete exists** for programs, cohorts, sessions and registrations. Programs/cohorts/sessions refuse while dependents exist (the schema cascades hard). **Registration delete deliberately does not refuse** — it erases the sign-up, its attendance and its certificate. `?delete_contact=true` also removes the person, but refuses for a contact with a staff account or registrations in other cohorts.
- **Cancel is reversible.** `register()` reinstates a cancelled row (same id, `created_at`, ticket token; `ticket_sent_at` cleared) instead of 409ing. Active duplicates still 409. Reinstating is capacity-checked.
- **Targeted open calls are a real restriction.** NEW `SessionCallTarget` (migration `b3e8a41d0014`) gates `list_available_sessions` and `register_interest` (404, not 403 — don't leak existence). **No target rows means unrestricted**, so every pre-existing call is unaffected. `reopen()` carries targeting over; pass `[]` to widen. `select_instructors(..., close_call=False)` keeps the call open while assigning.
- **Public ticket page**: `GET /public/ticket/{token}` and `/qr.png`, no auth — the token is the credential, exactly as when staff scan the same code. The frontend route is `/t/{token}`. Before this the QR and the emailed link both 404'd.
- **`issue_ticket(..., force=False)` is idempotent** on `ticket_sent_at`, and `safe_enqueue` only falls back to an in-process send when the ARQ enqueue didn't happen — together these stop the double-send that would have started the moment a real worker existed.
- **`RegistrationOut.certificate_issued`** is how you tell whether a student has a certificate. `certificate_url` is always null for them: student completion certs are emailed as a PDF attachment and never stored.

**2026-07-24 session-model rework (operator-initiated, full reasoning in `MASTER_EXECUTION_PLAN_V2.md` §B9/§DISCOVERIES) — read this before touching anything below that mentions "meeting" or "roster":**
- A cohort's teaching unit is now a first-class **`Session`** (own `title`, `material_url`, optional price override) — not a bare-date `SessionMeeting`. A single-day workshop is just a cohort with one session.
- **`CohortInstructor` is gone** (it was never wired to any endpoint). Instructor assignment is now **per-session** via `SessionInstructor`, and **a session can have multiple instructors** (lead/co) — this is deliberate, anticipating the Week 4 staffing marketplace where ops selects from a pool of interested instructors.
- **`RegistrationSession`** (new join table) lets a registration cover a subset of a cohort's sessions instead of all-or-nothing. An empty set (the common case) means "every session in the cohort" — this is the default so single-session workshops and registering before all sessions exist yet both need zero extra work.
- **No date_of_birth, no age band, no minor/guardian enforcement anywhere, period** — an explicit, permanent product decision, not a placeholder. Parent/guardian fields still exist on the forms but are always optional with zero system-side gating.
- **No separate Arabic name field** — `contacts.full_name_latin`/`full_name_arabic` collapsed into one `contacts.full_name`.
- **No consent tracking at all** — `ConsentRecord` writes removed from every registration flow (public form, desk, importer). The table still exists in the schema, untouched, waiting for the real consent service at CRM phase.
- **"Roster" is now "Registrations"** everywhere in the UI/API — it lists sign-ups, not attendance.
- **`programs.program_type` value `session` is now `info_session`** — renamed specifically to stop colliding with the new `Session` entity above.

**Local dev note (R2-1):** this dev environment has no VPS access, so Redis runs as a plain Docker container (`docker run -d --name spacepoint-redis-dev -p 127.0.0.1:6379:6379 redis:7-alpine`) — start Docker Desktop first if it isn't running. ## What this is

This domain is being built to replace SpacePoint's current registration process, which is entirely WhatsApp + Google Sheets + manual follow-up (there is no existing registration platform). It owns the commercial registration record (as opposed to spine's identity, or a future LMS's educational enrollment) and, once built out, the instructor-to-session staffing marketplace described in the V2 plan.

**Registration vs. enrollment**: a `registration` here is the commercial fact of signing up for a cohort. Whether that also creates an LMS enrollment (for course material) is a separate, later concern (V2 weeks 10+) — this domain never talks to the LMS directly.

## Key tables

| Table | What it holds |
|---|---|
| `programs` | A workshop/camp/course template (e.g. "CubeSat Workshop 2026-Q3"). |
| `cohorts` | One actual run of a program — real dates, location, capacity. `status` tracks the registration lifecycle; `staffing_status` tracks the *separate* instructor marketplace pipeline — a cohort can be `registration_open` while still `unstaffed`. `organization_id` + `visibility='private'` models a B2B-only cohort. |
| `sessions` | A real teaching unit inside a cohort — own `title`, `material_url`, optional price override, `UNIQUE(cohort_id, meeting_date, starts_at)`. Replaces the old bare-date `session_meetings`; a single-day workshop is a cohort with one session. |
| `session_instructors` | The staffing assignment (lead/co) for one session, once someone is picked — **a session can have multiple instructors**. Replaces `cohort_instructors` (never wired to anything, dropped). Distinct from `instructor_interests` below, which is still cohort-scoped (open question flagged in the plan: whether it should move to session-scope too). |
| `registrations` | The commercial record — **the ticket IS this row**, not a separate table. `ticket_token` is a long random credential (never a guessable sequential id); the QR code encodes a URL built from it. `payment_status` is recorded from day one even though the actual payment gate is deferred. `UNIQUE(contact_id, cohort_id)` — one registration per person per cohort. `ticket_sent_at` only gets set if the registration opted in via `send_ticket_email` (default true, but not forced). |
| `registration_sessions` | Which of a cohort's sessions a registration actually covers. **No rows for a registration = covers every session** (the default) — a caller only writes rows here to explicitly restrict to a subset. `check_in()` checks this before accepting a scan. |
| `attendance_records` | One student's attendance for one session (`session_id`, not `session_meeting_id`); `method` distinguishes a door QR scan from a manual mark. |
| `instructor_interests` | An instructor's "I'd like to give this" signal on an open-call cohort — the pre-selection marketplace step. |
| `session_reports` | A file an instructor/ops uploads after delivering a session. Not required to complete a cohort, just tracked. |
| `import_batches` | One upload of a bulk student sheet (a B2B client's roster, or a historical backfill). Always dry-run first; `counts` JSONB holds the preview/result. |
| `activities`, `activity_versions`, `activity_assignments` | Schema for the Kahoot-style live quiz facilitators will build — **schema only**, the engine that runs it live doesn't exist until weeks 13-14. `activity_assignments` has a CHECK constraint: exactly one of `program_id`/`cohort_id`, never both, never neither. |

## Gotchas for whoever builds R2-2+ on this

- **`registrations.contact_id`/`payer_contact_id`, `import_batches`, and everything else that FKs to `contacts.id`** must be checked against `MERGE_FK_REGISTRY` in `backend/app/services/spine/identity.py` (see `HANDOFF_SPINE.md`) — `registrations.contact_id`/`payer_contact_id` are already registered.
- **`cohorts.status` is `VARCHAR(24)`, not the `VARCHAR(16)` the original spec delta said** — `registration_open` alone is 17 characters. Caught by a functional insert test.
- **The ticket QR must encode the token/URL, never a guessable id or raw PII.** This came up explicitly when discussing the ticket design — do not follow any reference implementation that encodes name/email/phone directly into the QR payload; that leaks PII to anyone who scans or photographs the ticket, and if the "id" encoded is sequential/guessable, entry can be forged. `ticket_token` is a 64-char random string specifically to prevent this. `services/documents/ticket.py` generates it — reuse `generate_ticket_qr_png`/`ticket_url`, don't reimplement.
- **`attendance_records.recorded_by_user_id` is `NOT NULL`** with `ondelete='RESTRICT'` — unlike most "who did this" columns elsewhere in this codebase (which are nullable with `SET NULL`), you cannot delete a user who has recorded attendance. This was an intentional deviation from the spec's ambiguous punctuation (no explicit NULL marker on that field), on the reasoning that an attendance record with no recorder is meaningless. **`check_in()` will hard-fail (FK violation) if called with a fake/nonexistent `actor_user_id`** — always a real, logged-in staff user, never a placeholder.
- **`register()` doesn't take raw parent/guardian fields** — it takes an already-resolved `payer_contact_id`. Finding-or-creating the guardian contact and writing the `contact_relationships(guardian_of)` row is the *caller's* job (R1-5's public endpoint, or R2-3's desk UI). **There is no minor/guardian enforcement of any kind** — parent info is always optional, `register()` never checks for it, this is a permanent product decision (2026-07-24) not a gap. `register()` also takes `session_ids: list[UUID] | None` — omitted/empty means the registration covers every session in the cohort, writing `RegistrationSession` rows only when explicitly restricted.
- **`register()`/`issue_ticket()` raise `HTTPException` directly**, matching this codebase's existing service-layer convention (see `services/interns/epic.py`, `proposal.py`) rather than a separate domain-exception-translation layer. Status codes: 409 cohort full, 409 duplicate registration, 404 unknown ticket (check-in), 409 wrong-cohort or already-recorded (check-in), 409 "not registered for this session" if `RegistrationSession` rows exist and don't cover the scanned session. `check_in(db, token, session_id, actor_user_id)` takes a `session_id` against `sessions`, not the old `meeting_id`/`session_meetings`.
- **`issue_ticket()` never raises on a failed send** — it returns `False` and leaves `ticket_sent_at` NULL (verified against the real dev DB, not just the test DB: with `SMTP_USER`/`SMTP_PASSWORD` blank, as they are in dev today, it degrades gracefully every time). A registration always succeeds even if the email doesn't go out — don't couple the two.
- **Duplicate-registration handling needed the same per-row-SAVEPOINT pattern as `merge_contacts` (R1-3)** — catching the `UNIQUE(contact_id, cohort_id)` violation inside `db.begin_nested()`. If you write more services with a similar "catch this specific constraint violation" need, this is the established pattern, not raw `IntegrityError` handling on the outer transaction (which poisons the whole session for whatever the caller does next).
- **`identity_aliases` is now populated** — R1-5's `resolve_or_create_contact()` (in `services/spine/identity.py`) writes alias rows for whatever phone/email came in, whether the contact was matched or freshly created. **This is the one function that should own find-or-create-a-contact-from-raw-fields** — R2-2's bulk importer should call it too, not reimplement the pattern.
- **This app has no `/api` prefix anywhere** — every router mounts at root (`/auth`, `/ambassadors`, `/public`, etc.). The V1/V2 spec text writes every path as `/api/...`; that's aspirational, not real — drop the prefix to match what's actually deployed. Verified directly against `main.py`'s `include_router` calls, not assumed.
- **CORS for public forms is unioned into the app's one global `CORSMiddleware`**, via a new `PUBLIC_FORM_ORIGINS` env var (`app/core/config.py` — `public_form_origins` property) merged with the existing `cors_origins` in `main.py`. FastAPI's CORS middleware is one policy for the whole app; there's no clean per-route override, and widening it doesn't grant extra access — every protected endpoint still needs a valid JWT regardless of `Origin`.
- **Rate limiting is in-memory only** (`app/core/rate_limit.py`, `enforce_rate_limit()`) — a plain per-process dict, not shared across workers, lost on restart. This is the explicitly-flagged W1 interim; move to Redis once R2-1 lands. Don't rely on it holding up under multiple backend processes before then. If you write tests against it, give each test a distinct fake `X-Forwarded-For` IP — its state is module-level and persists across the whole pytest session, so tests sharing a bucket can spuriously 429 each other.
- **Manually testing anything with Arabic text on this Windows/Git-Bash setup**: don't embed literal Arabic characters in a `curl`/Bash command — it silently corrupts to `?????` before the request is even sent (a shell/curl argument-encoding artifact, not an app bug). Use a small Python/httpx script instead. Separately, `print()`-ing Arabic text to this console crashes with `UnicodeEncodeError` (cp1252 can't encode it) even when the underlying data is completely correct — compare by codepoint (`[hex(ord(c)) for c in s]`) or write to a file instead of printing directly.
- **`import_batches`'s dry-run and commit MUST stay structurally identical, not just tested for parity** — `services/sessions/importer.py::dry_run()` runs the exact same row-processing code as `commit_batch()` inside a SAVEPOINT it then rolls back, rather than maintaining two separate "preview" vs. "real" implementations. If you touch `_process_row`, both paths change together automatically; don't add preview-only logic that could drift from what actually commits. The stored/replayed row shape is always `_json_safe_raw()`'s output — never the parsed dict. **Template columns (as of the 2026-07-24 rework): `student_name, email, phone, city, parent_name?, parent_phone?, parent_email?`** — no `student_name_arabic`, no `dob_or_age`/DOB of any kind; parent columns are optional with zero minor-driven requirement.
- **A row matching an existing contact for a *different* cohort links (or queues a review); the same cohort resolves to `already_registered`** (the `UNIQUE(contact_id, cohort_id)` constraint) — don't read the spec's `create/link/review/error` disposition list as exhaustive for the same-cohort case.
- **Portal routes for R2-3/R2-4/R2-5 use the `operations`/`admin` role guard** (`require_operations` in `app/core/dependencies.py`, added alongside R1-1's `operations` role) — `admin` always passes every role check in this codebase; don't add a separate admin-bypass per route.
