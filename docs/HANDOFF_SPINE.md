## What this is

The one identity behind every person the platform ever deals with — a student registering for a workshop today may be an instructor next year, and both need to resolve to the same underlying record. Every other domain (sessions, and later CRM/marketing) points at a `contact_id`, never storing a name/phone/email of its own. This is what makes cross-program history and a future CRM possible without a rewrite.

Two things this domain deliberately does NOT do: (1) use name for matching, at all — not fuzzy, not as a hint, not in any form. Matching is email + phone only: an exact email match auto-merges (the only automatic outcome), a phone match always goes to a human via `merge_reviews`, and that's it — `contacts.full_name` (single field, no script/language distinction, see 2026-07-24 above) exists purely for a human to read and to search by (`GET /contacts?q=`). Operator call, 2026-07-22 — a false merge mixes two people's history and is hard to undo, and identity matching should key on a deterministic identifier the way any real system does, not on name similarity, even as a non-deciding hint. (2) no consent tracking *at all* as of 2026-07-24 (see above) — the `consent_records` table exists in the schema but nothing writes to it; the real consent service + `assert_can_send` gate ships at CRM phase start and will be its first writer.

## Key tables

| Table | What it holds |
|---|---|
| `contacts` | The identity itself — one `full_name` field (no Latin/Arabic split, no DOB/minor flag — dropped 2026-07-24), phones, email, roles array, lifecycle stage, optional org link. `merged_into_id` marks a soft-retired duplicate — never delete a contact. |
| `contact_relationships` | Household links (`guardian_of`, `child_of`, etc.) — how a parent's contact connects to their child's. Parent/guardian info is always optional on every registration path; nothing here is ever system-enforced by age. |
| `organizations` | Schools, sponsors, B2B clients, government bodies. Circularly linked with `contacts` (`primary_contact_id`) — see Gotchas below. |
| `consent_records` | Schema only — no code writes to this table as of 2026-07-24 (consent tracking was removed from registration entirely; see above). Will be the real consent service's table once that ships at CRM phase start. |
| `touchpoints` | Every interaction, every channel — the raw material a future CRM timeline/attribution is built from. `campaign_id`/`content_item_id` are plain UUIDs (no FK) until marketing tables exist. |
| `identity_aliases` | External identifiers that resolve to a contact (email, phone, WhatsApp id, Madar student id, social handles). `UNIQUE(alias_type, alias_value_hash)` is what makes exact-match lookup a simple query. |
| `merge_reviews` | A pending human decision when two contacts might be the same person. Never auto-resolved. |
| `contact_role_events` | (2026-07-24) One role gained/lost by a contact, timestamped, with source + who did it — the audit trail behind the Contacts page's "Role history" timeline. See `services/spine/role_history.py`. |

## Gotchas for whoever builds R1-4+ on this

- **Two circular foreign keys, both hand-fixed post-autogenerate.** `contacts.organization_id` → `organizations` is a normal FK; `organizations.primary_contact_id` → `contacts` is added via a separate `create_foreign_key()` call (constraint name `fk_organizations_primary_contact_id`) after both tables exist. Same pattern for `contacts.source_touchpoint_id` → `touchpoints` (constraint `fk_contacts_source_touchpoint_id`). **Alembic's autogenerate does not handle this correctly on its own** — it inlined the FK into the wrong table's `CREATE TABLE` in an order that would fail at runtime. If you ever regenerate a migration that touches these columns, check the emitted order by hand; don't trust autogenerate here.
- **`MERGE_FK_REGISTRY`** lives in `backend/app/services/spine/identity.py` — a list of `(table, column)` pairs, one entry per contact-referencing FK. `merge_contacts()` walks this list to repoint every reference when two contacts merge. **Any new column that FKs to `contacts.id` must be added to this list in the same migration that creates it** — it's how a merge doesn't silently leave stale references. Note `merge_reviews.candidate_a/candidate_b` are deliberately excluded (they're the merge audit trail itself, not live references).
- **Column widths**: `identity_aliases.alias_type` is `VARCHAR(32)`, not the `VARCHAR(24)` the original spec text said — `legacy_inventory_instructor` alone is 27 characters. Caught by a functional insert test, not by reading the DDL.
- **Nothing populates `identity_aliases` automatically.** `find_candidates`/`evaluate` in `identity.py` only *read* it — matching is a dead end until something writes email/phone alias rows when a contact is created or found. That's R1-4's job (the registration service), and R2-2's (the bulk importer): after creating or attaching to a contact, write an `IdentityAlias` row for whatever new phone/email came in (hash via the same `_alias_hash()` in `identity.py` — don't reimplement it). Skip this and `evaluate()` will return `NEW` for every single submission, forever, even genuine repeats.
- **Merging two rows that already share a unique-constrained relationship is handled, not just avoided.** `merge_contacts` processes every `MERGE_FK_REGISTRY` entry row-by-row inside a SAVEPOINT (`db.begin_nested()`), and on `IntegrityError` (winner already has an equivalent row — e.g. both winner and loser were independently recorded as `guardian_of` the same child) it deletes the loser's duplicate instead of crashing. If you add a new table to the registry with its own unique constraint touching the FK column, this generic handling already covers it — no per-table special-casing needed.
- **A minimal pytest harness now exists** (`backend/pytest.ini`, `backend/tests/conftest.py`) — the full CI/monorepo test setup is still V2 C0-2 (week 15+), this is just enough to run `pytest` locally against a dedicated `spacepoint_test` database (never `spacepoint_dev`). One real gotcha if you add more async fixtures: the engine must be created *inside* a fixture, not at module-import time, and `pytest.ini` needs both `asyncio_default_fixture_loop_scope = session` **and** `asyncio_default_test_loop_scope = session` (two separate settings in pytest-asyncio 1.4) — otherwise asyncpg breaks across tests with "attached to a different loop."
- **No `citext` extension.** `contacts.email` is a plain `String`, not case-insensitive at the DB level — case-insensitive matching is R1-3's job at the application layer (normalize before lookup), consistent with this repo not using any Postgres extension beyond `pgcrypto`.
- **`users.contact_id`** (R2-6, migration `c3e0a71d0003`) is nullable, `ON DELETE SET NULL`, and IS in `MERGE_FK_REGISTRY` — it has no uniqueness constraint, so a merge always safely UPDATEs it and the registry's generic delete-on-conflict fallback can never fire for this column. `scripts/backfill_user_contacts.py::backfill_user_contacts(db)` links any user without one; it's a plain create (no `evaluate()`/identity matching against existing contacts — a never-backfilled user has no prior submission history to reconcile against). Re-running the script is a no-op for already-linked users — verified against the real dev DB, not just tests.
- **`identity.py`'s alias-writing helper is now public: `ensure_alias(db, contact_id, alias_type, value)`** (renamed from `_ensure_alias` in R2-6 since a second caller — the backfill script — legitimately needed it). Same idempotent behavior as before: no-ops if the (type, value) pair is already recorded for any contact, never reassigns an existing alias's owner.
- **`routers/spine/contacts.py`/`merge_reviews.py` mount at `/spine`**, not `/api/spine` as the spec text says — consistent with the rest of this app having no `/api` prefix anywhere (see `HANDOFF_SESSIONS.md`).
- **`backfill_user_contacts()` re-syncs `contact_roles` for already-linked users too (added 2026-07-24), not just first-time links.** A user's `users.roles` can change well after their contact was created (e.g. an admin account manually granted more roles later) — without this, the contact's `contact_roles` silently goes stale and a role-filter search on Contacts will miss them, exactly what happened and got reported. The re-sync is **additive/union only** — it never removes a role already on the contact, so a role a human added directly on the contact (with no corresponding user role, e.g. `alumnus`) survives. The function's `linked` return value is unchanged in meaning (counts only brand-new links) so no existing caller/test needed updating. **This is not automatic on role change** — nothing calls it from `routers/admin/users.py` when a role is edited; it only catches up the next time the script is run by hand. If stale `contact_roles` becomes a recurring complaint, the real fix is wiring a call into the role-update endpoint (or a periodic job), not just re-running the script reactively.
